# Renaissance 88 — Repeatable page qualification protocol

The **88/88 candidate navigation smoke result** is backed by [the exact-head Chrome run](https://github.com/Emaren/app-prodn/actions/runs/40219717049), at source `6846438f9ef9b695cc2f45597ca9e26379a1c0df`. That result means navigation smoke in disposable PostgreSQL/browser conditions; it does **not** mean 88 engineering scores of 100, independent release authority, production security or financial activation.

## Cookie-cutter acceptance: one page at a time

1. Establish the canonical Index route and its **exact Git source tree**, current Next `BUILD_ID`, assurance profile and all required specialty gates. Reject drift before using any older browser evidence.
2. Run candidate desktop/mobile navigation, source/bundle, negative paths, accessibility, domain-specific database tests and performance cohorts. Preserve raw, bounded observations with SHA-256. **A smoke PASS earns zero certified points by itself**.
3. Review all **20 canonical rubric criteria** (30 correctness, 25 functionality, 20 performance, 15 maintainability, 10 tests/release); for each, obtain independently authenticated *dated* criterion evidence, review and approval under the existing Index verifier. Unknown remains unmeasured, not zero.
4. Review each route-specific assurance obligation (for betting: custody and nonmutation; for rankings: Steam and replay finality; for media: playback; for the Index: source-closure, score-verification, staleness). These are mandatory gates, not bonus scores.
5. Match the actual protected website deployment Git SHA, Next BUILD_ID, asset digest, operator approvals and rollback receipt. If a critical dependency changed since evidence capture, invalidate affected approval rather than relabel the old grade.
6. Admit a numeric score **only** through the existing independent publication/criterion verifier. 100 means every criterion demonstrably earned on that exact deployment, not a timeless guarantee of software perfection. Reinspect after significant source and runtime changes.

## Programmatic pilot

The additive CLI produces 88 route-specific, 20-criterion **worklists**, not approvals. It consumes the factory's `aoe2war.renaissance.public88.candidate-coverage.v1` JSON:

```bash
node scripts/renaissance_page_qualification.mjs \
  --coverage /path/to/renaissance88-coverage.json \
  --out /path/to/new-qualification-worklist.json
```

The output includes 88 per-route obligations, nine suggested ten-route-or-smaller batches, the candidate browser verdict, exact source/build identity, source freshness relative to the checkout and all specialization gates. It refuses unapproved scores, missing routes, contradictory totals, missing evidence digest or specialty claims invented from browser tests. Never feed the output into the protected scoring ledger as if it were an approved publication.

First suggested batch: `/kingdom-index`, `/requests`, `/`, `/kingdom-intelligence`, `/workshop`, `/academy`, `/library`, `/download`, `/watch`, `/betting-mechanics`. These are inspection priorities, **not** automatically high-scoring pages.

Central owns actual website release, final DocsV2 reseal, deployment authority and provenance. Tab A owns independent criterion admission; Tab D owns source-bound Chrome receipts. The financial WOLO path is independently HELD and must not piggyback on a website quality release.
